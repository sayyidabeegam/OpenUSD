# Chapter 36 — The Plugin System

> **Exam domain:** Customizing USD (6%) · **Objectives:** 3.1 · **Study day:** 11 · **Est. time:** 70 min
> **Prerequisites:** Ch 1 (the USD stack), Ch 6 (schemas), Ch 33 (resolvers), Ch 35 (ABI / `GetVersion`)

USD is not one binary that already knows every schema, file format, and resolver. Those are **plugins**. Obj 3.1 is "build a USD plug-in against a given version of USD" — Chapter 35 covered the *build*. This chapter covers the *discovery* file (`plugInfo.json`), the registry (`Plug.Registry`), the search path (`PXR_PLUGINPATH_NAME`), and the four plugin *jobs* you must name on the exam.

## Learning goals

- Read a `plugInfo.json`: `Name`, `Type`, `LibraryPath`, `Info.Types`, `bases`.
- List and look up plugins with `Plug.Registry`.
- Register a plugin at runtime (`RegisterPlugins`) and explain `PXR_PLUGINPATH_NAME`.
- Match a plugin job to its base type: schema, `SdfFileFormat`, `ArResolver`, Hydra/Sdr.

## Key terms

| Term | One-line definition |
|------|---------------------|
| **Plugin** | A library (or resource pack) USD discovers and may load |
| **`plugInfo.json`** | JSON catalog that names the plugin and the **types** it provides |
| **`Plug.Registry`** | Process-wide catalog of discovered plugins |
| **`PXR_PLUGINPATH_NAME`** | Env var: extra directories in which to look for `plugInfo.json` |
| **Type** | A C++/Tf type registered in `Info.Types` (e.g. `UsdGeomCube`) |
| **`bases`** | Parent type names in `plugInfo.json` (`SdfFileFormat`, `ArResolver`, …) |
| **Resource plugin** | No shared library; only files under `ResourcePath` |
| **Library plugin** | Has (or had) a `LibraryPath` to a `.so`/`.dll` |

## 36.1 Plugins and `plugInfo.json`

### 1. What is it?

A **plugin** is a unit USD can discover: usually a shared library plus a JSON file named **`plugInfo.json`**. The JSON lists the plugin's **name**, **type** (`library` or `resource`), where its files live, and which **Tf types** it provides (`Info.Types`).

### 2. Why do we need it?

Without a catalog, USD would have to hard-code every schema and format. Adding `Cube`, `.usda`, or a studio resolver would mean editing USD's core. `plugInfo.json` lets Pixar *and you* add types by dropping a folder on the plugin path (Obj 3.1).

### 3. Beginner explanation

A food-truck license taped to the window: name of the truck, what it is allowed to sell (tacos = `UsdGeomCube`, coffee = `SdfUsdaFileFormat`), and where the kitchen is (`LibraryPath` / `ResourcePath`). The city (USD) does not cook; it only reads licenses and then lets that truck operate.

*Where the analogy breaks:* some "trucks" in `usd-core` have an empty `LibraryPath` because the code is already linked into the Python package. The JSON still **declares the types**. Discovery and linking are separate.

### 4. Technical explanation

Verified on USD 26.08. A library plugin looks like this (trimmed from `sdf` in `usd-core`):

```text
{
  "Plugins": [
    {
      "Type": "library",
      "Name": "sdf",
      "LibraryPath": "",
      "ResourcePath": "resources",
      "Root": "..",
      "Info": {
        "Types": {
          "SdfUsdaFileFormat": {
            "bases": ["SdfFileFormat"],
            "extensions": ["usda"],
            "formatId": "usda",
            "primary": true
          }
        }
      }
    }
  ]
}
```

| Field | Meaning |
|-------|---------|
| `Plugins` | Array; one file may list several |
| `Type` | `library` (code) or `resource` (files only) |
| `Name` | Registry key (`usdGeom`, `sdf`, `ar`) |
| `LibraryPath` | Path to `.so`/`.dll`; empty in this wheel |
| `ResourcePath` / `Root` | Where extra files (and this JSON) live |
| `Info.Types` | Map of Tf type name → metadata |
| `bases` | What the type **is** (schema base, `SdfFileFormat`, `ArResolver`, …) |

A **root** `plugInfo.json` can be only includes:

```text
{ "Includes": [ "*/resources/" ] }
```

That is how `usd-core` discovers `usdGeom`, `sdf`, `ar`, … under `pxr/pluginfo/`. `usdGenSchema` emits the per-schema JSON (you will see `# Portions of this file auto-generated by usdGenSchema`).

Schema entries add `schemaKind` (`concreteTyped`, `singleApplyAPI`, …) and `alias` (the USDA type name `Cube`). File-format entries add `extensions` and `formatId`. Resolver entries list `bases: ["ArResolver"]`.

> [!VERSION] Verified on USD 26.08 `usd-core`. `LibraryPath` is empty for built-in plugins in the wheel; a studio C++ plugin you build (Ch 35) has a real library path.

### 5. Mental model

```text
  folder/
    plugInfo.json          <-- catalog (required)
    libStudio.so           <-- optional (library plugins)
    resources/             <-- optional extra files

  Info.Types["UsdGeomCube"].bases = ["UsdGeomGprim"]
  Info.Types["SdfUsdaFileFormat"].bases = ["SdfFileFormat"]
```

### 6. Simple example

`def Cube "Box"` works because the `usdGeom` plugin's `plugInfo.json` registers `UsdGeomCube` with alias `Cube`. No extra import is required for the *file* to parse; Python still `from pxr import UsdGeom` to *define* one.

### 7. USDA example

The layer below is legal **because** a plugin declared the `Cube` schema. The `plugInfo.json` itself is JSON, not USDA.

```usda
#usda 1.0
(
    defaultPrim = "Box"
)

def Cube "Box"
{
    double size = 2
}
```

- `Cube` — alias from `usdGeom`'s `Info.Types.UsdGeomCube`.
- If that plugin is missing, this file still *might* parse as a typed prim, but `IsA(UsdGeom.Cube)` and schema accessors will not behave as a built-in Cube.

### 8. Python example

```python
from pxr import Plug, Tf, Usd, UsdGeom

stage = Usd.Stage.CreateInMemory()
prim = UsdGeom.Cube.Define(stage, "/Box").GetPrim()
print("typeName", prim.GetTypeName())
print("IsA Cube", prim.IsA(UsdGeom.Cube))

reg = Plug.Registry()
plug = reg.GetPluginWithName("usdGeom")
print("plugin", plug.name)
t = Tf.Type.FindByName("UsdGeomCube")
print("Tf type valid", bool(t))
print("DeclaresType Cube", plug.DeclaresType(t))
print("schemaKind",
      reg.GetStringFromPluginMetaData(t, "schemaKind"))
```

**Expected output**

```text
typeName Cube
IsA Cube True
plugin usdGeom
Tf type valid True
DeclaresType Cube True
schemaKind concreteTyped
```

`GetStringFromPluginMetaData` reads the JSON field `schemaKind` for that type. `concreteTyped` is the IsA schema you author with `def Cube`.

### 9. Real-world use case

A games studio adds `StudioDestructibleAPI`. `usdGenSchema` writes a `plugInfo.json` whose `Types` entry has `bases: ["UsdAPISchemaBase"]` and `schemaKind: singleApplyAPI`. DCC and farm both find that file (Section 36.2). Artists then `def Mesh "Crate"` plus `apiSchemas = ["DestructibleAPI"]` without a USD source rebuild.

### 10. Common mistakes

> [!MISTAKE] Editing `plugInfo.json` `Name` to `usdGeom2` and leaving the library named `usdGeom`. The registry key and the library must match what you built.

> [!MISTAKE] Putting JSON next to the `.so` but naming it `plugin.json`. USD looks for **`plugInfo.json`**.

> [!MISTAKE] Assuming an empty `LibraryPath` means the plugin is broken. In `usd-core` it is normal.

### 11. Exam traps

> [!TRAP] "`plugInfo.json` is USDA." It is JSON. USDA *uses* the types it declares.

> [!TRAP] "`bases` is the prim path." It is the **Tf type** parent (`SdfFileFormat`, `UsdGeomGprim`, `ArResolver`).

> [!TRAP] "Every plugin must ship a `.so`." Resource plugins (`Type: resource`) have none.

### 12. Practice questions

**Q36.1-1.** Which file does USD read to discover a plugin's types?
A. `schema.usda` only
B. `plugInfo.json`
C. `CMakeLists.txt`
D. `defaultPrim`

**Q36.1-2.** Select two fields you expect on a file-format type in `plugInfo.json`.
A. `bases: ["SdfFileFormat"]`
B. `extensions` / `formatId`
C. `kind = component`
D. `metersPerUnit`

**Answers**

- **Q36.1-1: B.** The catalog is JSON. `schema.usda` is input to `usdGenSchema` (Ch 37).
- **Q36.1-2: A and B.** Kind and units are scene data, not plugin type metadata.

### 13. Exam takeaways

> [!KEY]
> - `plugInfo.json` catalogs `Name`, `Type` (library/resource), and `Info.Types`.
> - `bases` says what kind of plugin type you have.
> - Built-in `Cube` exists because `usdGeom` registered `UsdGeomCube`.
> - Obj 3.1: you ship this JSON with a library built against a **matched** USD.

## 36.2 `Plug.Registry` and `PXR_PLUGINPATH_NAME`

### 1. What is it?

**`Plug.Registry`** is the process-wide list of plugins USD has **discovered**. **`PXR_PLUGINPATH_NAME`** is the environment variable that adds extra directories to search for `plugInfo.json`. **`RegisterPlugins(path)`** does the same search at runtime (useful in tests and tools).

### 2. Why do we need it?

A studio plugin sitting in `/opt/studio/plugin` is invisible until that folder is on the search path. "My type does not exist" is usually a path problem, not a C++ problem (Obj 3.1, Obj 6.3).

### 3. Beginner explanation

`PXR_PLUGINPATH_NAME` is `PATH` for licenses. The registry is the clipboard of every license the city has already read. `RegisterPlugins("/opt/studio/plugin")` is handing the clerk one more folder *now*.

*Where the analogy breaks:* some hosts read the env var only at **startup**. Setting it after `from pxr import Usd` can be too late. `RegisterPlugins` is the explicit clerk.

### 4. Technical explanation

Verified on USD 26.08:

| Call | Result |
|------|--------|
| `Plug.Registry()` | The singleton registry |
| `GetAllPlugins()` | List of `Plug.Plugin` |
| `GetPluginWithName("usdGeom")` | One plugin or `None` |
| `GetPluginForType(Tf.Type)` | Which plugin owns that type |
| `FindTypeByName("UsdGeomCube")` | `Tf.Type` |
| `RegisterPlugins("/path/to/dir")` | Discovers `plugInfo.json` there; returns the new `Plugin` list |
| `plugin.Load()` | Load the library (`True` if ok) |
| `plugin.FindPluginResource("hello.txt")` | File under `ResourcePath` |
| `plugin.DeclaresType(tfType)` | Whether this plugin's JSON lists that type |

On this wheel, `GetAllPlugins()` returns **27** names, including `usdGeom`, `sdf`, `ar`, `usdPhysics`, `usdShade`, `usdHydra`, and several `*Validators`. `plugin.path` may be empty for built-ins; `resourcePath` points at `pxr/pluginfo/<name>/resources`.

`PXR_PLUGINPATH_NAME` is a **colon-separated** list of directories on Linux (semicolon on Windows). Each directory should contain a `plugInfo.json` (or an includes-style root). `Tf.GetEnvSetting("PXR_PLUGINPATH_NAME")` returned **`None`** in this venv — the variable is unset; built-ins still load from the wheel's `pluginfo` tree.

`RegisterPlugins` with a **resource** plugin (no `.so`) is enough to prove discovery. A C++ schema/resolver still needs `Load()` and a matching ABI (Ch 35).

### 5. Mental model

```text
  startup:  wheel pluginfo/  +  $PXR_PLUGINPATH_NAME
                 \                 /
                  v               v
                 Plug.Registry.GetAllPlugins()
                  ^
  tests/tools:    RegisterPlugins("/opt/studio/plugin")
```

### 6. Simple example

You create `demo_plug/plugInfo.json` with `"Name": "BookDemoPlugin"` and `Type: resource`. After `RegisterPlugins("demo_plug")`, `GetPluginWithName("BookDemoPlugin")` is not `None`, and `FindPluginResource("hello.txt")` returns that file.

### 7. USDA example

Discovery is not authored in USDA. A layer can *depend* on a plugin type; it cannot load the plugin.

```usda
#usda 1.0

def Sphere "Ball"
{
    double radius = 1
}
```

If `usdGeom` were not in the registry, `Sphere` would not be a first-class schema in this process. The file might still parse as a prim with that type name; Python `UsdGeom.Sphere` would not.

### 8. Python example

```python
from pxr import Plug
import os

reg = Plug.Registry()
names = sorted(p.name for p in reg.GetAllPlugins())
print("n built-in", len(names))
print("has usdGeom", "usdGeom" in names)
print("has BookDemoPlugin", "BookDemoPlugin" in names)

os.makedirs("demo_plug/resources", exist_ok=True)
open("demo_plug/plugInfo.json", "w").write("""{
  "Plugins": [
    {
      "Type": "resource",
      "Name": "BookDemoPlugin",
      "Root": ".",
      "ResourcePath": "resources",
      "Info": { "Types": {} }
    }
  ]
}
""")
open("demo_plug/resources/hello.txt", "w").write("hi\n")

new = reg.RegisterPlugins(os.path.abspath("demo_plug"))
print("registered", [p.name for p in new])
p = reg.GetPluginWithName("BookDemoPlugin")
print("isResource", p.isResource, "isPythonModule", p.isPythonModule)
hello = p.FindPluginResource("hello.txt")
print("resource exists", os.path.isfile(hello))
print("basename", os.path.basename(hello))
print("has demo after",
      "BookDemoPlugin" in [x.name for x in reg.GetAllPlugins()])
```

**Expected output**

```text
n built-in 27
has usdGeom True
has BookDemoPlugin False
registered ['BookDemoPlugin']
isResource True isPythonModule False
resource exists True
basename hello.txt
has demo after True
```

A resource plugin needs no compiler. A production resolver/schema plugin still needs the `.so` from Chapter 35, then this same `RegisterPlugins` or `PXR_PLUGINPATH_NAME`.

### 9. Real-world use case

The farm launcher exports `PXR_PLUGINPATH_NAME=/opt/studio/usd/26.08/plugin`. Every job — usdview, Maya, a Python publisher — sees `StudioResolver` and `StudioDestructibleAPI`. A TD who runs a laptop Python without that env var "cannot find" the custom type; `GetAllPlugins()` is the debug print (Obj 3.1).

### 10. Common mistakes

> [!MISTAKE] Setting `PXR_PLUGINPATH_NAME` to the `.so` file. It must be the **directory** that contains `plugInfo.json`.

> [!MISTAKE] Pointing the env var at `/opt/studio/plugin/resources`. The JSON is usually one level up, or the includes root is the parent.

> [!MISTAKE] Forgetting `RegisterPlugins` returns the **new** plugins only. `GetAllPlugins()` is the full list.

### 11. Exam traps

> [!TRAP] "`GetAllPlugins()` loads every `.so`." Discovery ≠ load. `isLoaded` can be False until `Load()` or first use.

> [!TRAP] "`PXR_PLUGINPATH_NAME` replaces built-ins." It **adds** search directories. This venv still has 27 built-ins with the var unset.

> [!TRAP] `RegisterPlugins` with a path that has no `plugInfo.json` silently giving you `StudioResolver`. It returns an empty list.

### 12. Practice questions

**Q36.2-1.** Where should `PXR_PLUGINPATH_NAME` point?
A. At `libStudioResolver.so`
B. At a directory that contains `plugInfo.json`
C. At the USDA entry layer
D. At `PYTHONPATH`

**Q36.2-2.** Select two true statements about this venv.
A. `GetAllPlugins()` has 27 built-in names including `usdGeom`
B. `RegisterPlugins` can add a `Type: resource` plugin at runtime
C. `PXR_PLUGINPATH_NAME` is required for `Cube` to exist
D. `GetPluginWithName` returns the Tf type `UsdGeomCube`

**Answers**

- **Q36.2-1: B.** Directory with the JSON, not the `.so`.
- **Q36.2-2: A and B.** Built-ins load without the env var; `GetPluginWithName` returns a `Plugin`.

### 13. Exam takeaways

> [!KEY]
> - Registry = discovered plugins; `GetAllPlugins` / `GetPluginWithName` / `GetPluginForType`.
> - `PXR_PLUGINPATH_NAME` adds JSON directories at startup.
> - `RegisterPlugins(dir)` is the runtime equivalent.
> - Discovery ≠ load; resource plugins prove the path without a compiler.

## 36.3 Plugin types (schemas, file formats, resolvers, Hydra)

### 1. What is it?

Four plugin **jobs** show up on the exam. They all use `plugInfo.json`, but they declare **different `bases`**:

| Job | Typical `bases` | What it adds |
|-----|-----------------|--------------|
| **Schema** | `UsdTyped` / `UsdGeomGprim` / `UsdAPISchemaBase` | Prim types and APIs (`Cube`, `MaterialBindingAPI`) |
| **File format** | `SdfFileFormat` | `.usda` / `.usdc` / `.usd` / `.usdz` (or a studio format) |
| **Resolver** | `ArResolver` (or `ArPackageResolver`) | How `@path@` becomes bytes (Ch 33) |
| **Hydra / Sdr** | Hydra scene index, `SdrDiscoveryPlugin`, … | Rendering / shader discovery |

Obj 3.1 is the *build*. Naming the job is how you choose the base class (Ch 37–38 fill each one in).

### 2. Why do we need it?

"Write a plugin" is not one API. A file-format plugin will never fix a missing texture (that is Ar). A resolver will never add `def Door`. The exam asks you to pick the **type of plugin**.

### 3. Beginner explanation

Four departments in city hall: zoning (schemas — what a building *is*), archives (file formats — how it is *filed*), address office (resolvers — how you *find* it), and the fire-inspection renderer (Hydra — how you *see* it). Same license paper (`plugInfo.json`); different department stamps (`bases`).

*Where the analogy breaks:* one JSON file can declare several types (the `sdf` plugin declares four file formats *and* `Sdf_UsdzResolver`).

### 4. Technical explanation

Verified on USD 26.08 `usd-core`:

**Schemas.** `usdGeom` declares `UsdGeomCube` with `schemaKind: concreteTyped` and alias `Cube`. `GetPluginForType(Tf.Type.FindByName("UsdGeomCube")).name` is `usdGeom`. Custom schemas: Chapter 37.

**File formats.** `Sdf.FileFormat.FindAllFileFormatExtensions()` → `['usd', 'usda', 'usdc', 'usdz']`. `FindByExtension("usda")` / `FindById("usda")` return the format object. `GetPluginForType(Tf.Type.FindByName("SdfUsdaFileFormat")).name` is `sdf`. Custom formats: Chapter 38.

**Resolvers.** `GetPluginForType(Tf.Type.FindByName("ArDefaultResolver")).name` is `ar`. `Sdf_UsdzResolver` is an `ArPackageResolver` for `@foo.usdz[bar.usda]@` (Ch 31, Ch 33). Custom resolvers: Chapters 33 and 38.

**Hydra.** This wheel still registers plugin `usdHydra` (shader discovery / generative-procedural API). It does **not** ship `UsdImaging` or a render window. Scene-index plugins (Obj 3.7) are Chapter 38; they need a full imaging build (Ch 35).

Decision table:

| You need to… | Plugin job | `bases` |
|--------------|------------|---------|
| Add `def Door` with schema properties | Schema | `UsdTyped` or `UsdAPISchemaBase` |
| Open `.mygeo` as a USD layer | File format | `SdfFileFormat` |
| Map `@chair@` to a database | Resolver | `ArResolver` |
| Generate Hydra prims at render | Scene index (Hydra) | Hydra scene-index base (Ch 38) |

### 5. Mental model

```text
  schema        -->  what a prim is     (Cube, PhysicsRigidBodyAPI)
  file format   -->  how a file is parsed   (.usda, .usdc, .usdz)
  resolver      -->  how @path@ is found
  Hydra         -->  how a renderer sees it
```

### 6. Simple example

Someone wants `.gltf` to `Usd.Stage.Open` without a converter. That is a **file format** plugin (`SdfFileFormat`), not a resolver (the path already points at a file) and not a schema (glTF already has meshes). A converter (Ch 27) is the other option if you do not want a plugin.

### 7. USDA example

Four jobs, one tiny stage: a schema type, a format implied by the file, an asset path for Ar, no Hydra in the file.

```usda
#usda 1.0
(
    defaultPrim = "Box"
)

def Cube "Box"
{
    asset preview = @./preview.png@
}
```

- `Cube` — schema plugin `usdGeom`.
- `.usda` — file-format plugin `sdf`.
- `@./preview.png@` — resolver plugin `ar` (default filesystem).
- Drawing the cube — Hydra / `UsdImaging` (not in `usd-core`).

### 8. Python example

```python
from pxr import Plug, Tf, Sdf

reg = Plug.Registry()


def owner(type_name):
    t = Tf.Type.FindByName(type_name)
    plug = reg.GetPluginForType(t)
    return plug.name if plug else None


print("Cube owner", owner("UsdGeomCube"))
print("USDA format owner", owner("SdfUsdaFileFormat"))
print("default resolver owner", owner("ArDefaultResolver"))
print("extensions", sorted(Sdf.FileFormat.FindAllFileFormatExtensions()))
print("usda by ext",
      Sdf.FileFormat.FindByExtension("usda").formatId)
print("usdc by id", Sdf.FileFormat.FindById("usdc").formatId)

g = reg.GetPluginWithName("usdGeom")
print("usdGeom declares Material",
      g.DeclaresType(Tf.Type.FindByName("UsdShadeMaterial")))
print("has usdHydra",
      "usdHydra" in [p.name for p in reg.GetAllPlugins()])
print("has usdPhysics",
      "usdPhysics" in [p.name for p in reg.GetAllPlugins()])
```

**Expected output**

```text
Cube owner usdGeom
USDA format owner sdf
default resolver owner ar
extensions ['usd', 'usda', 'usdc', 'usdz']
usda by ext usda
usdc by id usdc
usdGeom declares Material False
has usdHydra True
has usdPhysics True
```

`UsdShadeMaterial` lives in plugin `usdShade`, not `usdGeom`. That is `DeclaresType` earning its keep.

### 9. Real-world use case

A CAD vendor ships: (1) a **file format** plugin so `.sldprt` opens as a stage, (2) a **schema** for CAD identifiers, (3) nothing in Ar if paths are ordinary files. A cloud studio instead ships only an **ArResolver** so `@part/bolt@` hits object storage, and they convert CAD offline (Ch 27). Pick the job from the problem, then build against 26.08 (Ch 35).

### 10. Common mistakes

> [!MISTAKE] Writing a resolver to "add a Door prim." Resolvers find files; schemas define prims.

> [!MISTAKE] Writing a file-format plugin to "search `/opt/assets`." That is Ar search paths / a custom resolver (Ch 33).

> [!MISTAKE] Expecting `usdHydra` in this wheel to open usdview. Discovery of a Hydra *schema* is not an imager.

### 11. Exam traps

> [!TRAP] "All plugins subclass `UsdTyped`." Only typed schemas do.

> [!TRAP] "`.usd` is a fourth encoding plugin besides USDA/USDC/USDZ." `.usd` is `SdfUsdFileFormat` (`formatId` `usd`); it *contains* USDA or crate (Ch 31).

> [!TRAP] Obj 3.7 (scene index) is satisfied by `plugInfo.json` for `usdGeom`. Scene indices are a Hydra plugin family, Chapter 38.

### 12. Practice questions

**Q36.3-1.** You need `Usd.Stage.Open("hero.mygeo")` to work. Which `bases`?
A. `ArResolver`
B. `SdfFileFormat`
C. `UsdAPISchemaBase`

### 13. Exam takeaways

> [!KEY]
> - Four jobs: schema, file format, resolver, Hydra — distinguished by `bases`.
> - Built-in extensions: `usd`, `usda`, `usdc`, `usdz` from plugin `sdf`.
> - `GetPluginForType` tells you who owns a Tf type.
> - Obj 3.1: build *that* job's plugin against the host USD version.

## Chapter review

**Summary**

- Plugins are discovered via `plugInfo.json`; `Info.Types` + `bases` declare the job.
- `Plug.Registry` lists them; `RegisterPlugins` / `PXR_PLUGINPATH_NAME` add more.
- This wheel: 27 built-ins; `LibraryPath` often empty; resource plugins need no `.so`.
- Schema → `usdGeom` / `usdPhysics` / …; formats → `sdf`; resolver → `ar`; Hydra → `usdHydra` (no `UsdImaging` here).
- Obj 3.1 = matching ABI (Ch 35) **plus** this discovery story.

**If you see… → think…**

| If you see… | Think… |
|-------------|--------|
| `plugInfo.json` | Plugin catalog, not USDA |
